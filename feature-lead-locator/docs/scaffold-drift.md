# Scaffold drift: edits that an upgrade will revert

`scaffold.metadata.json` marks **137 of 144** generated files as `replace`.
Running `feature-scaffold apply --upgrade` against this repo rewrites every one
of them from the template, silently discarding local changes. Only 7 files are
`create_if_missing` and therefore safe to own:

```
frontend/src/App.tsx
frontend/src/components/FeatureHomePage.tsx
frontend/src/components/BackendHealthCard.tsx
backend/app/api/feature.py
backend/app/services/feature_service.py
jobs/refresh_source_caches/runner.py
workers/score_on_search/handler.py
```

Files created *after* generation (everything under
`backend/app/infrastructure/sources/`, `backend/app/models/*.py` except
`example.py`, `backend/alembic/versions/`, `backend/tests/test_sources_*.py`,
`conftest.py`, `docker-compose.yml`) are not in `managedFiles` at all and are
left alone by an upgrade. Feature logic belongs there by default.

## Before running an upgrade

```bash
feature-scaffold plan --config ../scripts/lead-locator-feature.json \
  --repo . --diff --fail-on-modified
```

`--fail-on-modified` stops if a managed file changed locally. Re-apply the
edits below afterwards.

## Managed files edited locally, and why

| File | Edit | Breaks if reverted |
|---|---|---|
| `backend/requirements.txt` | added GeoAlchemy2, h3, shapely | Models and tiling fail to import |
| `backend/pyproject.toml` | same deps + respx | Test suite cannot run |
| `backend/app/models/__init__.py` | import the four PostGIS models | **Dangerous** — alembic autogenerate stops seeing the models and emits `drop_table` for every one of them |
| `backend/alembic/env.py` | `include_object` filter + `search_path` pin | **Dangerous** — autogenerate emits `drop_table` for ~40 PostGIS `tiger`/`topology` tables |
| `backend/alembic.ini` | DB URL -> PostGIS :5435 | Migrations target the wrong database |
| `backend/app/platform/database/config.py` | default DB URL -> PostGIS :5435 | Service connects to `localhost:5432/app` |
| `backend/.env.example` | ports, `DATABASE_URL`, data-source settings | New clones get a broken config |
| `backend/tests/test_feature.py` | `test_health` asserts the route that actually serves | Test fails against a shadowed endpoint |
| `frontend/package.json` | `--port 3600` (was 3200) | Port collision with asset-inventory |
| `frontend/vite.config.ts` | `localPort = 3600`, CORS origins | Same |

| `scripts/run-local.sh` | ports 8600/3600 (were 8100/3200) | Same |

## The two dangerous ones

Both make `alembic revision --autogenerate` produce a destructive migration
that looks routine:

1. **`app/models/__init__.py`** — alembic's `env.py` does `from app.models
   import *` to populate `Base.metadata`. If the upgrade reverts this file to
   importing only `ExampleRecord`, autogenerate sees four tables in the
   database that are absent from the metadata and helpfully offers to drop
   them.

2. **`alembic/env.py`** — the `postgis_tiger_geocoder` extension rewrites the
   *database's* `search_path` to `"$user", public, topology, tiger`. Alembic
   reflects the search_path, so without the pin it treats every `tiger` and
   `topology` table as an unqualified table missing from the models. Verified:
   it emitted `drop_table('edges')`, `drop_table('county_lookup')` and ~40
   more.

   Note the pin is applied via libpq `connect_args={"options":
   "-csearch_path=public"}`, **not** by issuing `SET search_path` on the
   connection. Under SQLAlchemy 2.0 that statement opens an implicit
   transaction before alembic's own `begin_transaction()`, so alembic's commit
   lands on a nested transaction and every migration silently rolls back —
   logging `Running upgrade` and exiting 0 while writing nothing.

**Always read an autogenerated migration before applying it.** Neither problem
announces itself.

## Worth fixing upstream

These are template bugs, not local quirks — every feature generated by the tool
inherits them:

* `deployment.port` in the feature JSON drives the manifest and Terraform but
  not local dev config, so `package.json`, `vite.config.ts`, `.env.example` and
  `run-local.sh` all ship with another feature's ports (8100/3200).
* `frontend/.env.example` points `VITE_API_BASE_URL` at `:8000` — the
  bootstrap API — rather than the feature's own backend.
* The database capability generates no `DATABASE_URL` in `.env.example`; the
  default in `app/platform/database/config.py` is `localhost:5432/app`.
* `app/api/feature.py` and `app/api/health.py` both define `GET /health`. The
  latter shadows the former, and the generated `test_health` asserts the
  unreachable one.
* `get_settings()` is `@lru_cache`d with no test fixture to clear it, so
  generated auth tests silently ignore their own `monkeypatch.setenv` calls —
  `test_items_allowed_with_platform_admin` passed without exercising the
  platform.admin path at all.
* `ExampleRecord` ships with no migration, leaving autogenerate permanently
  dirty.
